01开场：先把问题讲窄

建议讲稿约 90 秒

“今天我想讲的不是模型会不会写代码，而是另一个更工程化的问题：模型能不能把一件需要持续几个小时的软件工程工作，可靠地推进到可以验收的终点？”

“这和更长 context 不完全是一回事。真正难的是，模型在过程中要记住现在已经验证了什么、哪些假设失败了、最好的版本在哪里、用户是否改了需求，以及现在还有没有时间做高风险重构。”

“SWE-Marathon、FrontierSWE、SWE-Together 正好从三个方向切开这个问题：完整项目、专家级连续指标、以及真实用户多轮纠偏。最后我想落到两件实事：我们怎样自己造任务、怎样把跑出来的轨迹蒸馏回 agent。”

转场
“先不要急着看 task 名称。我们先问：为什么已有的 SWE-bench 还不足以回答这个问题？”
若被问：长程是否就是 context 更长？

不是。更长 context 只是存储历史的条件，不保证模型会维护正确的工作状态。长程能力还包括状态压缩、证据更新、回滚、验证和停止决策。

02三组 benchmark 的分工

建议讲稿约 3 分钟

“SWE-bench 的价值没有变：它第一次比较严肃地把真实 GitHub issue 变成了可测 patch。但它偏向一个局部闭环——找到问题、改一个 patch、跑测试。”

“SWE-Marathon 往前走一步，问的是模型能不能完成一整项工程：可能是产品、迁移、训练或系统优化。FrontierSWE 则问，做成以后能不能在性能、兼容性、research metric 这些连续指标上真正推进，而不是只拿一个二值通过。SWE-Together 再加上现实世界最容易被 benchmark 忽略的变量：用户会在中途改口、追问和限制 scope。”

“所以我把它们看成一个闭环：SWE-Marathon 决定工作对象，FrontierSWE 决定如何给进展计分，SWE-Together 决定谁能改变目标。”

转场
“这个区分不靠 abstract 最好理解。我们直接看几个任务：它们的难点究竟落在什么地方？”
若被问：FrontierSWE 为什么任务少？

因为它故意把任务推到更高成本、更强专家背景的区域。目标不是覆盖海量 issue，而是让模型差异能在协议兼容、正确性受限性能优化、研究实验等难题上显现出来。

03案例：怎样把技术细节讲成人话

案例 A：Slack clone —— “产品题”实际在测故障下的一致性

建议讲稿约 3 分钟

“Slack clone 听起来像一个前端 demo，但任务真正要验收的是一个小型分布式系统。它要求三个 HTTP 节点、一个 IRC gateway、浏览器 UI；并且用户连到不同节点后，消息顺序不能乱，某个节点或广播组件死掉后，系统还得继续工作。”

“这里的 dense sequence 可以理解为频道消息的连续编号：如果你看到 101、102、104，就说明系统在故障或切换中丢了事件。hidden verifier 会专门打这种地方。于是 agent 不只是做功能列表，而要知道什么时候应该停止加 UI，转而验证 failover。”

这例子要落的结论
“长程 agent 需要学会把 chaos test 当需求的一部分，并在局部功能与系统性风险之间分配时间。”

案例 B：Revideo —— “更快”只有在“仍然正确”时才有意义

建议讲稿约 3 分钟

“Revideo 的任务是优化视频渲染。一个很自然、但危险的做法是跳帧、降低画质或者绕开某些昂贵步骤。表面上速度快了，实际已经不是同一个任务。”

“它的评分顺序非常关键：先在 hidden scenes 上过视觉正确性，比如 SSIM；只有所有场景都正确，才计算 speedup。换句话说，速度是被 correctness gate 锁住的连续 reward。”

“因此 agent 的正确工作方式是：先测 baseline，再提出具体瓶颈假设，再做很小的实验，发现指标回退要能回滚，并且持续维护当前最佳版本。这个过程比最后那一处优化代码更值得训练。”

案例 C：pi-mono —— 用户的新消息会改写任务目标

建议讲稿约 3 分钟

“pi-mono 一开始只要求调查 tool stall 并写 memo；随后用户又要求先写 failing test、不使用 interactive metadata、改为 sequential、测试必须走真实代码路径。这意味着最终的正确实现，如果只看第一句 instruction，甚至像是越界。”

“SWE-Together 的价值就在这里：它不是把 user message 当作附带的聊天记录，而是把它当作任务状态的更新。训练数据如果只保留 turn 0，就会错误地奖励‘闭门造车’。”

转场
“这些例子说明，长程任务不是 prompt 写长一点。那么如果我们要自己做，任务资产具体应该长什么样？”
案例不要讲太散

时间紧时只讲这三个；被问“迁移/研究任务呢？”再补 BioFabric 的 parity 与 parameter-golf/pcqm4mv2 的最终 artifact contract。

04自建任务：把“现实工作”变成可靠评测

建议讲稿约 4 分钟

“我们不能先写一条很长的 prompt，再称它是 long-horizon benchmark。一个可靠任务至少有六类资产：objective、固定环境、visible feedback、hidden verifier、reference/oracle、以及 anti-cheat 设计。”

“我认为顺序尤其重要：先做 oracle，并跑一个 NOP baseline。oracle 必须稳定通过，NOP 必须明显低分。否则我们不知道低分是模型不行，还是题本身不稳；更不知道高分是不是因为 verifier 有洞。”

“然后才用多个 agent pilot，人工读失败日志。这一步看起来慢，实际是在避免把任务歧义、环境故障和模型能力失败混为一谈。最后冻结 task version、repo commit、image digest、verifier hash、harness hash，才可以规模化采数据。”

转场
“题目可信以后，下一步不是简单保存完整聊天记录。我们要问：到底该留下什么，才让下一个模型学到工程过程？”
若被问：为什么还要 NOP baseline？

NOP 是“什么也不做”的基线。它能发现 verifier 是否过松、环境是否自带答案，或任务初始状态是否已经接近完成。若 NOP 有高分，训练模型会被奖励到错误行为。

05Trajectory 与蒸馏：模型到底学什么

建议讲稿约 6 分钟

“我不建议把一条成功轨迹原封不动丢进 SFT。成功 rollout 里经常有反复搜索、无效命令、自动重试和偶然蒙对；失败 rollout 里也可能有非常好的诊断。真正的训练单位应该是一个 episode：模型在某个可描述的状态下，看到了什么证据，做了什么行动，行动结果怎样，为什么决定保留、回滚或切换方向。”

“这会导出四类数据。第一类是 action SFT，学习下一步高信息增益动作。第二类是 state compression，学习把几个小时历史压缩成当前目标、已工作/已失败、修改过的文件、最佳版本和下一步。第三类是 verifier critic，让模型解释为什么一个‘看起来变快’的实验仍然不可接受。第四类是 stop/continue policy，专门训练不要过早提交，也不要在失败实验上无休止堆补丁。”

“在实践上，成功的局部 episode 可以做 SFT；同一状态下的好坏分支做 preference；verifier subscore 和 hard fail reason 给 critic；新的内部 rollout 再做 online RL。它们不是互斥，而是从模仿、判断到探索的层层递进。”

若被问：为什么要保存 best checkpoint？

长程 agent 很容易在最后一次冒险修改后把已经过关的版本改坏。best checkpoint 是“迄今为止证据最好的工作区”，让 agent 能安全探索并回滚；它还提供很好的 stop/continue 监督信号。

06接回 harness：最后落到可做的动作

建议讲稿约 4 分钟

“最稳的路线不一定是马上重新训练一个 foundation model，而是先把长程工作纪律做进现有 harness。例如让 Claude Code 的任务一开始就生成 acceptance ledger，自动维护目标、约束、test、风险、实验与 best checkpoint；在提交前强制 final checklist；重复失败就换诊断路径。”

“这样我们马上获得两样东西：更可靠的 agent 行为，以及结构更干净的 rollout 数据。但要诚实记录哪些步骤是模型做的、哪些是 wrapper 自动做的，否则会把 harness 的能力误记为模型能力。”

“如果之后要换成自训 student，Claude Code 这条路径的难点不是改一个 base URL，而是 Anthropic Messages、streaming、tool use 和长 session 的兼容性。做真正 on-policy RL 时，自定义 agent 通常更干净，因为能直接保留 token、mask 和 logprob。”

收尾句
“我想把最重要的一点再重复一次：长程软件工程的训练对象不是更长的文本，而是一个能被 verifier、用户与状态共同约束的工程过程。”

07术语速查：遇到不懂的词，直接这样讲

Benchmark 基准 / 评测集

一组有固定任务、环境和评分规则的考试题，用来比较不同模型或 agent。

你可以这样说：“它不只是题目列表；它还规定了模型在哪个环境做题、什么算做对。”

Agent 智能体

不是只输出一段文字的模型，而是能读文件、编辑代码、运行命令、看结果、再决定下一步的系统。

你可以这样说：“模型负责思考和选择，agent 是让它在电脑里实际做事的外壳。”

Harness Agent harness / 脚手架

围绕模型的执行框架：工具定义、权限、system prompt、会话管理、checkpoint、日志和验证流程。Claude Code、Harbor adapter 都可以视为 harness。

你可以这样说：“同一个模型，放进不同 harness，像同一个人拿到不同工具和流程，工作质量可以差很多。”

Docker / Image Digest 容器 / 镜像指纹

Docker 把代码、依赖、系统工具装进可重复运行的隔离环境；image digest 是这个环境内容的不可变指纹。

你可以这样说：“它保证今天和下周跑的是同一台‘虚拟电脑’，避免依赖版本悄悄变化。”

Verifier 验证器 / 评分程序

独立于 agent 的测试与计分代码。它从最终工作区或运行结果判断任务是否完成，并可给 partial score、hard failure 或 anti-cheat 结果。

你可以这样说：“verifier 相当于自动阅卷老师；比模型自称‘我完成了’可靠得多。”

Visible / Hidden Test 可见 / 隐藏测试

visible test 给 agent 调试方向；hidden test 不暴露，防止模型只针对已知断言写特化答案。

你可以这样说：“可见测试教你怎么走，隐藏测试检查你是不是只背了答案。”

Oracle 与 NOP Baseline 标准解 / 什么都不做基线

oracle 是可信参考解，应稳定满分；NOP baseline 则不做任何修改，应低分。两者共同验证题目与 verifier 是否健康。

你可以这样说：“先确认满分答案能过、空白答案过不了，才有资格说这是一道好题。”

Reward / Continuous Reward 奖励 / 连续奖励

reward 是给 agent 行为的数值反馈。连续奖励不只区分过或不过，还可按 speedup、held-out metric 等连续数值区分进展大小。

你可以这样说：“二值分数只能告诉你及格没；连续分数还能告诉你谁做得更好。”

Correctness Gate 正确性门槛

只有先满足正确性，后续指标才有资格计分。Revideo 中只有画面仍正确，speedup 才有价值。

你可以这样说：“先证明没有把题做坏，才讨论你做得有多快。”

Held-out Set 留出集

训练/调参期间不暴露的一批数据，用于最后判断模型是否真的泛化，而不是记住开发集。

你可以这样说：“像考试前不能看的正式卷，用来防止只对练习题调参。”

Trajectory / Rollout 轨迹 / 一次执行过程

trajectory 是 agent 完成任务时的完整行动—观察历史；rollout 是从初始状态跑出一条这样的轨迹的一次尝试。

你可以这样说：“不是最后的 diff，而是从拿到任务到提交前每一次看、改、测、回滚的工作过程。”

Durable State / State Compression 持久状态 / 状态压缩

将长历史压成可长期保存、可重启的工作摘要，例如目标、已验证事实、失败方向、改过的文件、最佳版本和下一步。

你可以这样说：“相当于工程师离开前写的交接笔记，回来后不必重新读完所有终端输出。”

Checkpoint / Best-so-far 检查点 / 当前最优版本

checkpoint 是工作区或模型参数在某个时刻的可恢复快照；best-so-far 是截至当前证据最好的 checkpoint。

你可以这样说：“先把能跑的版本存档，再冒险尝试；失败随时能回到已验证的最优点。”

SFT、DPO 与 Online RL 三类训练方式

SFT 模仿高质量动作；DPO/偏好训练在好坏选择之间拉开差距；online RL 让模型在环境中实际探索，并根据 reward 更新策略。

你可以这样说：“先教它模仿好员工，再教它辨别好坏，最后让它在真实沙盒里练习。”

Critic / Process Reward 过程评判器 / 过程奖励

critic 评价某一步决策是否合理；process reward 不只奖励最终成功，也奖励或惩罚中间的验证、回滚、风险控制等过程。

你可以这样说：“不是只看最后交卷对不对，还要教它在中间有没有用正确的方法做题。”

Reward Hacking / Anti-cheat 刷分 / 反作弊

模型找到指标漏洞而非真正完成任务，例如视频任务跳帧降质、研究任务偷看 hidden label、代码任务改测试或伪造输出。anti-cheat 是防护这些路径的设计。

你可以这样说：“模型像非常聪明的考生；我们必须先想它可能怎么钻空子。”

Contamination 数据污染

训练数据中已包含评测题、隐藏答案或其关键线索，导致评测分数不再代表真实泛化能力。

你可以这样说：“如果考题或答案进了训练集，分数变高不等于模型真的变强。”

Parity Test 行为一致性测试

把新实现与参考实现喂同一输入并比较输出，检验迁移/重写后行为是否一致。BioFabric 的 byte-level parity 要求尤其严格。

你可以这样说：“不是看新代码看起来像不像，而是看给同样输入时行为能否对齐。”

Dense Sequence / WebSocket Replay 连续序号 / 断线补放

dense sequence 要求频道事件编号无缺号；WebSocket replay 是客户端断线或切节点后，补回缺失消息的机制。

你可以这样说：“它保证聊天记录不会因为切服务器而漏消息或乱序。”

Anthropic-compatible Endpoint Anthropic 兼容接口

一个网关实现 Claude/Anthropic 所需的 Messages、streaming、tool use、错误与会话语义，让 Claude Code 等客户端能调用非 Anthropic 的模型。

你可以这样说：“不是把 URL 换掉就行；客户端和服务端必须说同一种工具调用和流式协议语言。”

0830 秒救场卡片

如果被打断，只记住这 5 句

  • 长程不是长文本，而是持续维护可验证工作状态。
  • SWE-Marathon 测完整施工，FrontierSWE 测专家级连续进展，SWE-Together 测用户在环。
  • 好任务先要 oracle 过、NOP 低、hidden verifier 稳，再谈采训练数据。
  • 好 trajectory 保存状态转移与验证证据，不是只保存最终 patch 或聊天记录。
  • 先把 checkpoint、verification、rollback 等纪律做进 harness，再考虑重训模型。
