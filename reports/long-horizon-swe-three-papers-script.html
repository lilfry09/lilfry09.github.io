把三组长程 SWE 工作讲清楚

SWE-Marathon、FrontierSWE、SWE-Together：作者动机、任务构造、评分机制、真实案例与各自的局限。

讲法：不要把它们讲成三篇摘要。每篇只回答四个问题：为什么做？拿什么任务测？怎么判断做得好？它揭示了长程 Agent 的哪一个缺口？

00使用方式与时间分配

2 min开场：长程到底是什么先给地图
7 minSWE-Marathon完整项目
7 minFrontierSWE专家级进展
7 minSWE-Together用户在环
4 min横向比较与收尾三句话带走

01开场：先把“长程”讲明白

可以直接讲约 90 秒

“今天讲的不是模型会不会写一段代码，而是一个更接近真实工程的问题：模型能不能把一件需要持续几个小时的软件工作，可靠地推进到可以验收的终点？”

“SWE-bench 主要问：一个真实 issue 能不能修好。今天这三组工作把问题扩大了：SWE-Marathon 问一个完整项目能不能做完；FrontierSWE 问在专家级系统、性能和研究任务上能推进多少；SWE-Together 问用户中途改变要求时，Agent 能不能继续做对。”

“所以我不把它们看成三个相似榜单，而把它们看成长程能力的三个切面：工作长度、问题难度、目标是否变化。”

转场
“先从最接近传统软件工程 benchmark 的一组开始：SWE-Marathon。”

02SWE-Marathon：从修 patch 到做完整项目

主线讲稿约 7 分钟

“SWE-Marathon 对应 arXiv:2606.07682。它的出发点很直白：真实工程师拿到一个任务以后，通常不是立刻改某一行代码，而是要先理解系统、启动环境、搭骨架、做实验、处理失败，最后再交付。短 issue benchmark 没有覆盖这段过程。”

“因此它选择了项目级任务：产品克隆、库重写、ML 训练、系统优化。论文初版报告 20 个超长程任务，并把任务放进固定的 Docker/Harbor 环境，用 visible checks 帮 Agent 找方向，再用 hidden verifier 做最终验收。”

“这里的关键不是任务描述有多长，而是任务内部有很多互相依赖的验收条件。模型如果只做 UI，不处理故障；只训练出 checkpoint，不满足提交路径；只让 Rust 编译，不保持 Java 行为，都不能算真正完成。”

任务例子 1 · slack-clone

聊天应用其实是在测分布式系统

“它要求三个 HTTP 节点、一个 IRC gateway 和浏览器 UI。消息要有连续的频道序号，WebSocket 切到另一个节点后要补回消息；杀掉节点或广播组件以后，其他路径还要继续工作。”

“我要强调的是，这不是功能列表题。Agent 必须决定先搭什么骨架，什么时候去做 chaos test，怎么在 API、持久化、实时推送和 UI 之间分配时间。”

任务例子 2 · biofabric-rust-rewrite

重写任务的核心是行为一致

“Rust skeleton 能编译不代表完成。它还要参考 Java 实现，保持公共 API 和 BIF/NOA/EDA、layout、analysis、alignment 等输出一致，甚至接近 byte-level parity。这个任务测的是先找行为真相、再逐模块对齐，而不是凭感觉翻译代码。”

任务例子 3 · parameter-golf

ML 任务还有最终产物契约

“语言模型训练要满足 held-out 指标和 checkpoint 大小限制；最终脚本和 checkpoint 必须放在 verifier 规定的位置。一个模型训练得好但提交物不可加载，仍然是失败。这说明长程工程包括实验、资源预算和交付包装。”

这篇工作的一句话结论

SWE-Marathon 测的是项目级持续执行：能不能把很多小闭环组织成一个最终可验收的大闭环。

如果有人问局限

任务人工构造成本高、数量有限、不同 verifier 不完全同质；最终 resolved 也不自动说明中间过程高效，更不能单独区分模型能力和 harness 托举。

转场
“Marathon 把工作变长了，但专家级任务还有另一个问题：如果只看最终 pass/fail，做出部分真实进展的 Agent 会被低估。FrontierSWE 就从评分方式开始改。”

03FrontierSWE：把“进展”本身做成分数

主线讲稿约 7 分钟

“先澄清一个身份问题：FrontierSWE 目前更准确地说是 Proximal Labs 的 benchmark 项目、官方技术博客和开源任务仓库，不是和另外两篇同形态的 arXiv 论文。它公开的首发版本有 17 个高难任务。”

“它的作者动机是：当 Agent 开始做协议兼容、性能工程和 ML research 时，二值 resolved 太粗。一个 Agent 可能没完全跑通 PostgreSQL 兼容，但已经覆盖了很多 public behavior；另一个连程序都启动不了。它们不应该得到相同的信息。”

“所以 FrontierSWE 不是用一个统一分数强行评价所有任务，而是按任务族定义 reward：implementation 看测试覆盖，performance 先过 correctness 再算 speedup，research 看 held-out metric 和最终可执行产物。”

任务例子 1 · postgres-sqlite-wire-adapter

兼容性是一个面，不是一条功能

“底层使用 SQLite，但要让 PostgreSQL 客户端以为自己连上了 PostgreSQL。隐藏测试会覆盖 startup/auth、simple query、prepared statement、transaction、catalog、Unix socket 和 cluster lifecycle。优先级不是先实现一个很炫的 SQL feature，而是先让 psql select 1、initdb、pg_ctl start/stop 跑起来，再逐步扩大兼容面。”

任务例子 2 · revideo-perf-opt

快但错，得分仍然是零

“Revideo 允许你优化 Canvas、browser-node 传输、WebSocket 或 FFmpeg，但不能跳帧、降画质或改 API。Verifier 先在 hidden scenes 上检查视觉正确性，只有 correctness 全过，speedup 才计分。因此它训练的工作顺序是 baseline、profile、小实验、正确性 gate、保存最好版本。”

任务例子 3 · pcqm4mv2-autoresearch

研究任务也必须像软件一样可交付

“研究约束包括 closed-data、2D-only、参数上限和不能使用外部 checkpoint。最终不只看 dev MAE，还检查 submission/checkpoint 目录和 predict.py 的 inference contract。这在测可执行研究，而不是让 Agent 写一段看起来合理的模型介绍。”

这组工作的一句话结论

FrontierSWE 测的是正确性约束下的专家级进展：不是做了多少动作，而是把真实指标推进了多少。

如果有人问局限

任务少且高度异质，连续分数之间不天然可比较；硬件和专家成本高；当前主要证据来自官方项目材料和仓库，而不是一篇经过同样评审流程的论文。

转场
“前两组都默认任务目标在开始时已经写好。但真实用户经常会中途追加要求，甚至改变实现边界。SWE-Together 处理的就是这个变量。”

04SWE-Together：用户会改变任务

主线讲稿约 7 分钟

“SWE-Together 对应 arXiv:2606.29957，公开任务和 Hugging Face 数据集包含 109 个多轮任务。它指出一个常被 benchmark 忽略的事实：真实用户不会在第一句 instruction 里把所有要求说完。”

“用户会追问为什么这样改，会说不要动外部依赖，会指出测试 mock 太多，也会在调查之后要求继续实现。如果只保存 turn 0 和最终 patch，就看不到 Agent 是否听懂纠偏。”

“它的关键设计是 progressive reveal：Agent 先拿到初始指令，后续 user simulator 根据会话条件逐步发送追问、纠偏或追加要求。这样测的是收到新证据后能不能更新计划，而不是从一开始猜中完整剧本。”

任务例子 1 · comfyui-triton-windows-amd-fix

代码改动小，交互目标不小

“Windows + AMD 下的 Triton 编译错误，reference patch 可能只有两行：把 load 改成稳定 base pointer 上的 indexed load，并删除指针自增。但用户会追问为什么；如果 Agent 跑去修改 Triton 外部依赖，用户会把它拉回当前 repo。”

任务例子 2 · qwen3-moe-gguf-dequant

相似算子连续实现，还要服从测试协议

“会话从一个 IQ dequant 开始，随后扩展到多个 IQ layout。用户会纠正 PYTHONPATH、要求 elemental PyTorch operations，并追问性能瓶颈究竟在 dequant 还是 test-side quantization。Agent 必须同时保持实现细节和沟通目标。”

任务例子 3 · pi-mono-parallel-tool-stall

“不要实现”可能被后续要求合法改写

“一开始用户只要调查 memo，后来明确要求 failing test、sequential tool execution 和真实 session wiring。最终实现不是 scope creep，而是最新用户意图下的正确工作。”

这篇工作的的一句话结论

SWE-Together 测的是随时间更新的用户意图：Agent 不只要忠于第一句 instruction，还要忠于当前最新且完整的需求。

如果有人问局限

User simulator 仍是对真实会话的建模，可能无法覆盖所有人类表达；交互目标如何评分也比纯测试更主观；simulation prompt 一旦泄漏 reference fix，评测就会失真。

05横向比较与收尾

最后 4 分钟可以这样讲收束

“三组工作并不是在争夺同一个榜单。SWE-Marathon 把工作对象变成完整项目；FrontierSWE 把进展变成正确性约束下的连续指标；SWE-Together 把用户的新消息变成任务状态更新。”

“如果用三个动词总结：Marathon 是做完，FrontierSWE 是推进，Together 是跟随。它们共同说明，未来的 SWE Agent 评测不会只有 prompt 到 patch，而要观察 Agent 如何在一个可执行世界里持续维护目标、证据和交付状态。”

长程能力不是把 context window 拉长，而是让 Agent 在时间变长、问题变难、需求变化时，仍能把工作带到可验证的终点。
结束语
“所以这三组工作真正扩展的，不只是任务规模，而是我们对‘软件工程能力’这个词的定义。”

06现场术语救场

Benchmark带固定任务、环境和评分规则的评测集，不只是题目列表。
Verifier自动阅卷程序：独立检查代码、测试、性能或最终产物，不能只听 Agent 自称完成。
Hidden test不公开的测试，用来防止 Agent 只针对可见断言写特化答案。
Correctness gate先证明结果仍然正确，之后性能 speedup 才有资格计分。
Held-out调参时不暴露的留出数据，用来判断研究结果是否真的泛化。
Parity test新实现和参考实现用同一输入，比较输出是否一致；重写任务常用。
Progressive reveal用户消息逐步出现，测 Agent 收到新证据后是否更新计划。
