SIX BENCHMARKS · FROM EXPLORATION TO ULTRA-LONG PROJECTS

Coding Agent 的六类工程能力

统一比较任务规模、token 消耗、long-horizon 程度、完整测评时间，以及 task、query 与 trajectory 的构造方式。

Ffry · 2026-07-21 · 组会讲稿版
一句话结论：六个 benchmark 不在同一时间尺度：SWE-Explore 只测“能否找到代码”，SWE Atlas 测非修复型工程工作，SWE-Together 测用户在环，ProgramBench 测从零重建，FrontierSWE 与 SWE-Marathon 则把单任务推到 20 小时或数千万累计 token。

01六个 benchmark 到底分别在问什么？

它们不是六个相似榜单，而是从仓库探索到完整项目的六个不同切面。

SWE-MARATHON能不能把项目做完？任务对象是完整软件项目；重点是长时间施工、跨模块推进和最终验收。
FRONTIERSWE能不能取得专家级进展？任务对象是协议兼容、性能工程、研究实验；重点是正确性之后还有多少连续收益。
SWE-TOGETHER用户改口后还能不能做对？任务对象是多轮真实会话；重点是意图更新、scope 纠偏和交互成本。
SWE ATLAS不修 issue，还会什么？Codebase Q&A、写测试、重构，强调工程质量而不只是功能修复。
PROGRAMBENCH能否从零重建程序？只给可执行文件与文档，让 Agent 自主设计并复现外部行为。
SWE-EXPLORE能否先找到正确上下文？给 issue 与仓库，在固定行预算内返回最相关的文件和行区间。

它们共同反对一个过于简单的评测方式：给模型一句 instruction，最后只看 patch 是否通过。但要注意，SWE-Explore 本身不是 end-to-end 长程任务；它把长程修复中的“探索”阶段单独抽出来测。

讲解提示
可以把六者排成一条能力链：找到代码 → 理解/测试/重构 → 跟用户协作 → 从零造程序 → 在专家任务上推进 → 完成超长项目。

02SWE-Marathon：把评测单位从 patch 拉到完整项目

身份：arXiv:2606.07682 对应的论文与开源 benchmark。论文初版报告 20 个超长程任务，运行在 Harbor/Docker 环境中。

作者为什么要做它？

SWE-bench 已经把真实 GitHub issue 变成了可执行评测，但大量题目仍然是相对局部的 bug fix：找到位置、改 patch、跑测试。作者认为，这无法代表真实工程中“先理解一个系统，再连续数小时推进多个依赖环节”的工作。

SWE-Marathon 因而故意选择人类专家需要几十小时的项目：产品克隆、跨语言重写、机器学习训练、系统优化。它关心的不是模型某一次修改够不够聪明，而是模型能不能在长时间内维持目标、建立可运行 baseline、处理失败并最终交付。

任务是怎么构造的？

组成作用
instruction.md给出最终目标、外部接口和约束，但不暴露隐藏测试的具体断言。
task.toml固定时间、CPU/GPU、内存、网络、镜像等运行条件。
Docker 环境冻结代码、依赖和工具链，让不同 Agent 在同一个“世界”里工作。
visible checks提供基本反馈，让 Agent 知道环境是否能启动、方向是否完全错误。
hidden verifier最终验收功能、鲁棒性、性能或产物契约，避免只针对可见测试写答案。
oracle / NOP参考解必须稳定通过；什么都不做必须低分，用来证明任务和评分器健康。

三个任务能说明什么？

TASK · slack-clone

看起来是聊天应用，实质是分布式产品验收

Agent 要实现注册、workspace、频道、DM、thread、reaction、file、search 等完整功能，同时运行三个 HTTP 节点和一个 IRC gateway。隐藏测试还会断开节点、切换 WebSocket、杀掉广播组件，检查消息能否 replay、频道序号是否连续，以及 SQLite fallback 是否在故障后继续工作。

它在测：Agent 会不会先搭可启动骨架，把 API、持久化、实时推送和 UI 分层推进，并把故障恢复当成需求而不是最后的意外。

TASK · biofabric-rust-rewrite

Java → Rust：重写不是“翻译语法”，而是恢复行为

初始 Rust skeleton 可以编译，但大量函数是 todo!()。Agent 需要参考 Java BioFabric 和 Network Alignment plugin，实现 Rust library 与 CLI，并在 layout、analysis、alignment 等输出上通过接近 byte-level 的 parity test。

它在测：Agent 能否找到参考实现的行为真相、锁定公共 API、逐模块对齐语义，而不是一次性重写后靠猜测修测试。

TASK · parameter-golf

ML 任务：实验结果和最终提交契约同样重要

Agent 要在指定数据与算力预算下训练语言模型，提交训练脚本和不超过 32MB 的 checkpoint，并让 hidden held-out 指标达到门槛。一个模型即使训练指标很好，只要 checkpoint 放错、推理入口不完整或依赖散落，最终仍然失败。

它在测：实验设计、资源预算、checkpoint 管理和最终 artifact contract 能否形成闭环。

这篇工作真正告诉我们什么？

它最重要的贡献不是“题目更大”，而是把完整工程任务做成了可重复运行、可最终验收的环境。论文观察到，长 rollout 的大量 token 消耗在历史工具输出、上下文回放与维持工作状态，而不只是生成新代码。这说明长程瓶颈不能简单归因于模型不会写某个函数。

读完应记住SWE-Marathon 测的是项目级持续执行：能不能把几十个互相依赖的小闭环组织成一个最终可验收的大闭环。

局限：它没有证明什么？
任务数量较少且人工构造成本高；不同项目的 verifier 和难度并不完全同质；最终 resolved 也无法自动说明中间过程是否高效、是否靠 harness 托举。不同版本的官网、仓库与数据快照还可能发生任务数量或实现细节漂移。

03FrontierSWE：不只问“做没做成”，还要问“推进了多少”

身份说明：FrontierSWE 当前更准确地说是 Proximal Labs 发布的 benchmark、官方技术博客和开源任务仓库；它不像另外两项那样对应同形态的 arXiv 论文。首发公开 17 个高难任务。

作者为什么要做它？

当 coding agent 已经开始挑战大型重构、协议实现、性能优化与研究实验时，短任务加二值 resolved 很难区分 frontier model：两个模型都可能“没完全做完”，但一个已经打通核心协议，另一个连程序都无法启动；它们不应该得到完全相同的信息。

FrontierSWE 因而把任务做得更少、更贵、更接近专家边界，并给不同任务族设计不同的连续评分。核心问题从“有没有交卷”变成“在正确性约束下，取得了多少可测进展”。

三类任务怎样评分？

任务族典型评分为什么不能统一为 pass/fail
Implementation编译、协议兼容、回归测试、TAP/功能测试的通过率。即使没有全部完成，覆盖多少公共行为仍然是有意义的能力差异。
Performance先过 correctness gate，再按 hidden workloads 上的 speedup 等连续指标计分。否则 Agent 会通过跳帧、降质、删功能等方式刷速度。
ML Researchheld-out metric、参数/资源限制和最终 inference contract。研究进展天然是连续的，同时必须防止偷看数据或提交不可复现产物。

三个任务能说明什么？

TASK · postgres-sqlite-wire-adapter

用 SQLite 做底层，却让 PostgreSQL 客户端相信它连上了 PostgreSQL

Agent 要写 Zig 单二进制，按 argv[0] 扮演 postgres、initdb、pg_ctl。隐藏 verifier 会跑 startup/auth、simple query、prepared statement、transaction、catalog、Unix socket、CLI 和 cluster lifecycle，甚至接入 PostgreSQL regression/TAP 测试。

它在测：Agent 是否理解“兼容面”的优先级：先打通 psql select 1 和进程生命周期，再逐步扩大协议与 catalog 覆盖。

TASK · revideo-perf-opt

性能优化：更快之前必须先证明仍然正确

Agent 可以优化 Canvas、browser-node 传输、WebSocket 或 FFmpeg 路径，但不能跳帧、降画质或改变 API。Verifier 先用 hidden scenes 比较视觉和行为正确性，只有全部过关才计算几何平均 speedup。

它在测：baseline、profile、局部实验、correctness gate 与 best-so-far 管理，而不是一次性写出“看起来更快”的 patch。

TASK · pcqm4mv2-autoresearch

研究任务：分数、资源和可执行提交缺一不可

Agent 要在 closed-data、2D-only、参数上限等约束下做 molecular graph regression，并提交能够独立加载 checkpoint、读取 hidden input、输出预测的最小 inference package。

它在测：能否把读数据、设计模型、跑实验、保留最佳 checkpoint 和封装最终提交组织成可执行研究，而不是只提出一个模型点子。

这组工作真正告诉我们什么？

FrontierSWE 的核心创新在评分思想：对于专家任务，progress 本身应被测量，但连续 reward 必须被正确性和反作弊约束。它把 verifier 从“最后判卷”提升为任务定义的一部分。

读完应记住FrontierSWE 测的是正确性约束下的专家级进展：不是做了多少动作，而是把真实指标推进了多少。

局限：它没有证明什么？
任务少且高度异质，单一总分很难解释；不同任务的 reward 标度并不天然可比较；任务成本和硬件需求高；当前主要证据来自官方项目材料和仓库，而不是一篇结构完整、经过同样评审流程的论文。

04SWE-Together：把真实用户重新放回 Agent 循环

身份：arXiv:2606.29957 对应的论文、开源任务与 Hugging Face 数据集。论文公开 109 个以真实 user-agent session 为核心的任务。

作者为什么要做它？

传统 benchmark 通常把用户需求压成一条静态 instruction。但现实中用户会追问“为什么这样改”、限制“不要动外部依赖”、指出“你的测试 mock 太多”、或者在看过调查结果后要求继续实现。任务目标不是在第一轮就完全固定的。

如果评测只保存初始 prompt 和最终 patch，就会漏掉 Agent 是否听懂纠偏、是否解释关键修改、是否遵守新的 scope；甚至会把遵循后续要求的正确实现误判为偏离初始指令。

数据和任务是怎么组织的？

资产包含什么
初始 instructionAgent 在 turn 0 得到的任务，不提前泄漏所有后续用户要求。
Repo + base commit固定真实代码库的初始状态。
User simulation prompt根据原始会话中的触发条件，在合适时机追问、纠偏、追加要求或保持沉默。
Frozen goals / scoring targets把功能目标、scope、解释义务和用户意图覆盖写成可复核的评分标准。
Verifier + reference patch同时检查代码结果和关键目标是否满足，而不是只比较文本。

它的关键机制是 progressive reveal：Agent 先得到第一轮需求，后续用户消息只在相应条件出现后发送。这样评测的是“收到新证据后是否调整”，而不是要求模型从一开始就猜中完整剧本。

三个任务能说明什么？

TASK · comfyui-triton-windows-amd-fix

Patch 只有两行，但 scope 和解释同样是目标

问题是 Windows + AMD GPU 下的 Triton 编译错误。Reference patch 只需要稳定 base pointer 的 indexed load，并删除循环中的指针自增。但用户会追问为什么要这样改；如果 Agent 跑去修改 Triton 外部依赖，又会明确要求在当前 repo 内解决。

它在测：小 patch 不代表小任务；Agent 还要解释原因、服从 scope，并在错误方向上及时收缩。

TASK · qwen3-moe-gguf-dequant

需求逐步扩展，测试协议和性能解释不断被校正

会话从修一个 IQ3_XXS dequant 开始，随后扩展到多种 IQ layout；用户会提醒直接使用当前目录测试、不要用不符合要求的 F.embedding，并追问性能瓶颈究竟在 dequant 还是 test-side quantization。

它在测：Agent 能否在相似但不同的实现间持续保持细节正确，并根据用户反馈修正测试和性能判断。

TASK · pi-mono-parallel-tool-stall

初始“只调查”可以被后续用户要求合法地改写

会话最初要求调查并写 memo，随后用户要求先加 failing test、不要 interactive metadata、让工具 sequential、测试走真实 session wiring。最终 reference patch 确实包含实现与测试。

它在测：用户消息是目标函数的更新；Agent 不能只忠于 turn 0，而要忠于当前最新且完整的用户意图。

这篇工作真正告诉我们什么？

SWE-Together 把软件工程 Agent 从“独自解题者”改成“协作参与者”。代码是否正确仍然重要，但能否解释、遵守 scope、响应用户纠偏，也是完成任务的一部分。

读完应记住SWE-Together 测的是随时间更新的用户意图：同一个动作在 turn 0 可能越界，在用户明确追加要求后却可能变成正确行为。

局限：它没有证明什么？
User simulator 仍是对真实会话的模型化，可能无法复现所有人类表达；任务评分需要把代码正确性与交互目标结合，主观性高于纯测试；如果 simulation prompt 泄漏 reference fix 的变量名或代码形状，也会降低评测可信度。

05横向比较：三组工作拼出怎样的长程 SWE 图景？

维度SWE-MarathonFrontierSWESWE-Together
核心问题完整项目能否完成专家任务推进多少多轮用户意图能否跟随
时间尺度小时级项目施工高成本系统/性能/研究实验多轮会话中的目标演化
反馈visible checks + hidden final verifiercorrectness-gated continuous reward用户消息 + frozen goals + verifier
典型失败项目分解失控、过早结束、故障路径遗漏快但错、研究产物不可执行、只实现局部兼容忽视纠偏、scope 越界、只完成初始指令
最重要贡献把完整项目做成可执行评测把专家级 progress 做成受约束连续指标把用户意图更新做成 benchmark 事件
三者共同推动了一个变化：评测对象从“最终 patch”变成“Agent 在可执行世界中持续推进任务的能力”。

如果组会上只需要带走三句话：SWE-Marathon 关心能不能做完；FrontierSWE 关心在保证正确的前提下能推进多少；SWE-Together 关心用户改变要求以后还能不能继续做对。
