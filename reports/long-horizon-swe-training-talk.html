01 / 为什么现在需要它

旧 benchmark 主要问：
“能不能修好一个 patch？”

SWE-BENCH

真实 issue
→ 可评分 patch

把真实仓库、issue 与测试绑定起来，奠定了 coding agent 的基本评测范式。

缺口

数小时的工程
如何不失控？

真实任务要读系统、搭骨架、实验、回滚、验证；成本大量花在维持工作状态。

新问题

在过程里
可靠地推进

不仅要会改代码，还要听用户纠偏、守住约束、保存最好版本、知道何时停。

核心区别：long-horizon ≠ long context；瓶颈是工作循环质量。02
讲法：SWE-bench 没有过时，它解决的是“真实 patch”。新工作不是替代它，而是把任务范围从一个 patch 扩展到一段完整、可验证的工程过程。

03 / 任务案例一 · SWE-Marathon
SLACK-CLONE · 约 60 小时专家工作量

“做个聊天应用”
为什么是一道长程题？

3 个 HTTP 节点 + IRC gateway；浏览器 UI；Docker/Harbor 环境；hidden verifier 最终判定。

它要求 workspace、频道、DM、thread、reaction、search、file、slash command… 但真正的难点是：节点切换后的 WebSocket replay、跨节点 dense sequence，以及广播组件失效后 5 秒内 SQLite fallback 仍保持 fan-out。

  • 产品面：API + UI + IRC
  • 分布式面：多节点、故障、顺序
  • 验收面：API / chaos / Playwright / UI rubric
先可启动先打通最小 skeleton，不让局部功能吞噬全局进度。
分层推进API、持久化、实时、UI 分层，持续跑小验证。
故障即需求不能只通过可见 browser test；hidden 更可能打在 failover。
任务来源：SWE-Marathon tasks/slack-clone 的 instruction、task.toml 与 verifier 约束。04
补充两个任务类型：biofabric-rust-rewrite 是 Java → Rust 的语义迁移，要求 API 和 byte-level parity；parameter-golf 则要求在资源与 checkpoint 契约下完成 ML 训练。它们把“长程”覆盖到迁移与研究工程。
04 / 任务案例二 · FrontierSWE
REVIDEO-PERF-OPT · 正确性约束下的性能优化

性能不能只问：
“有没有变快？”

TypeScript 视频渲染链路：Puppeteer、Vite、Canvas、WebSocket、FFmpeg。

Correctness gate

候选版本必须在 hidden scenes 上保持视觉与行为正确；不能跳帧、降质、改 API。

→
Continuous reward

只有 gate 全过，才按各场景几何平均 speedup 计分。错了就是 0。

这迫使 agent 学会：先建 baseline → 做假设 → profile → 小实验 → 守住质量 gate → 保存 best-so-far。

同族例子：postgres-sqlite-wire-adapter（协议兼容面）；pcqm4mv2-autoresearch（hidden held-out + 最终 artifact contract）。05
重点：这张页是连续 reward 的意义。对性能任务，若先奖励速度、再检查正确性，模型会自然学出“快但错”；评分顺序本身就是训练信号。
05 / 任务案例三 · SWE-Together
PI-MONO-PARALLEL-TOOL-STALL · 用户意图会变

最终 patch 一样，
对话行为可能完全不一样。

任务最初只要调查 memo，真实会话随后追加：failing test、不要 interactive metadata、改为 sequential、测试走真实路径。

如果只保存 turn 0，后面的实现会被错误判为 scope creep；如果只看最终 diff，又会漏掉用户对“不要 mock”“两个 submission 都尝试”的持续纠偏。SWE-Together 把用户消息本身变成 trajectory 的状态转移。

  • 初始目标：调查，不实现
  • 中途更新：先写 failing test
  • 质量约束：真实 wiring，不要重造 mock
  • 最终实现：session 设置 sequential

训练对象从 “prompt → patch” 变成 “intent(t) → action(t) → observation(t) → intent(t+1)”。

另见 comfyui-triton-windows-amd-fix 的 scope 纠偏、qwen3-moe-gguf-dequant 的多轮实现与性能追问。06
讲法：这其实是最容易被忽视的部分。一个成熟的 agent 不只是解决初始问题，它还要在用户改变约束后，承认前面的假设不再成立并调整轨迹。
06 / 如果我们自己做：先做可靠任务，再做训练数据

一个长程任务不是 prompt，
而是一套可执行资产。

OBJECTIVE
目标、约束、接口、可见反馈；只写 outcome，不泄漏 hidden verifier。
ENVIRONMENT
固定 repo commit、Docker/image digest、数据与工具链、网络政策和资源上限。
VERIFIER
先写 oracle，再跑 NOP；产品任务测 API+UI+resilience，性能先 correctness gate，研究任务看 held-out。
ANTI-CHEAT
hidden asset 隔离、source/dependency/hash scan、读写与网络策略、reward-hack threat model。
PILOT
用多个 agent 试跑并人工读失败日志：区分任务歧义、环境问题与模型能力边界。
FREEZE
冻结 task_hash + verifier_hash + harness_hash；之后的每条 rollout 都必须可追溯。
一句工程原则：oracle 稳定过、NOP 明显低分，任务才配成为训练数据。
SWE-Marathon 的贡献流程、FrontierSWE 的 task-specific reward、SWE-Together 的 frozen goal/user simulator 都体现此结构。07
实践建议：先从内部 backlog 或真实 debug 会话中选 5–10 题，不要先“编题”。评测可靠性是训练价值的前提。

强调：成功 trial 也含有大量不该模仿的重复、误读和 harness 自动动作；失败 trial 也可能有高质量诊断。不要把整条 trajectory 当一个正样本。
08 / 蒸馏：切 episode，不是整条吞

把一条长轨迹拆成四类训练信号。

ACTION SFT下一步做什么输入任务 + durable state + observation，学小步、有信息增益的行动，而不是整段 bash 模仿。
STATE COMPRESSION现在到底进展到哪把几小时历史压为 goal / working / failing / changed files / next；解决上下文污染与记忆漂移。
VERIFIER CRITIC为什么这次“看似进步”仍不可接受例如 speedup 上升但 SSIM fail，必须判为失败；把 subscore 与 hard-fail 变成过程反馈。
STOP / CONTINUE何时回滚、何时提交偏好稳定 full gate、best checkpoint、明确回滚；惩罚未验证提交与失败实验上的补丁堆叠。

训练配方：局部好 episode 做 SFT；同状态好坏分支做 preference；verifier 做 critic；新 rollout 做 online RL。

需过滤 oracle/solve.sh、verifier tampering、环境异常、harness 自动补跑；公开 benchmark 的轨迹不可再用于无污染原 benchmark 报分。09
落到工程：如果现在没有 RL 基础设施，先做 state compression + action SFT + verifier critic，通常已经能显著提升“有条理地做事”的表现。
09 / 怎么 hack 进 Claude Code 一类 harness

先增强系统，
再考虑换模型。

最稳的路径不是立刻重训 foundation model，而是把从 trajectory 蒸馏出的长程工作纪律写进 CLAUDE.md、skill、MCP 或 wrapper。

这样能立刻收集更干净的 on-policy 数据；同时标明“模型决策”与“harness 自动行为”的边界。

ACCEPTANCE LEDGER
  • 目标、约束、visible tests、hidden-like risks
  • 重要编辑前保存 checkpoint
  • 实验记录：假设 / 命令 / 结果 / 是否保留
  • 自动维护 best-so-far，不默认提交 current workspace
  • final checklist；剩余预算低时禁止大重构
  • 重复失败时切换诊断路径
若替换 Claude Code 后端，网关需要真兼容 Anthropic Messages、streaming、tool use 与长 session；仅有 OpenAI chat-completions 通常不足。10
两条路：1) 不换模型，增强 harness；2) 用 Anthropic-compatible gateway 接入 student model，保留 stream-json/session JSONL 并转 ATIF。严肃 on-policy RL 时，更干净的是自定义 Harbor agent，直接保留 token ids/logprobs。
10 / 一个可执行的最小实践路线

从 5–10 道内部真题开始，
用两轮迭代闭环。

WEEK 1

选真题

内部 backlog、性能瓶颈、迁移、真实用户 debug。按 repo family 做 train/eval 隔离。

WEEK 2

任务资产

Docker + visible smoke + hidden verifier + oracle/NOP + anti-cheat threat model。

WEEK 3–4

收轨迹

接入 ledger；多 agent 多预算 pilot；人工标注失败类型和高价值 episode。

WEEK 5–6

蒸馏与回测

先 SFT/critic/harness policy；在未见任务上测完成率、验证纪律、恢复率与成本。

评测指标别只看 pass@1：还要看 verification coverage、best-checkpoint recovery、user-correction compliance、cost-to-resolution。

产出不只是一个 leaderboard，而是一套可复用任务资产、可审计轨迹与可以不断再训练的系统闭环。11
收束到团队行动：先把这套工程制度跑通，再谈大规模训练。要先知道“一个好 episode 是什么”，才有资格多采几十万条。
11 / TAKEAWAY

长程软件工程能力，
训练的是一种工程过程。

模型当然要会写代码；更重要的是，它要能在一个尚未结束的现实里维护状态、相信证据、接受纠偏，并把系统带到可验证的终点。

可执行任务 + 分阶段反馈 + 用户纠偏
+ 状态快照 + verifier = 可训练的长程能力
